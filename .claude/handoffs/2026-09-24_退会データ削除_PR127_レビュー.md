## レビューの結論（判定確定済み）

### D1 — Functions の TOCTOU で `publicProfiles` が復活する → **reject（存在しないコーナーケース）**
- **退会フロー自身の発火は安全**。step1 が `try await` で完了してから step2 に入るため、
  Firestore の強整合により `reconcileFollowCounters` は必ず `exists == false` を読む（general の反論が正しい）
- 第三者の同時操作の窓は `Promise.all` の get と set の間＝**1 RTT（数十 ms）**。
  ユーザー約80人・フォローイベント数件/週では到達しない
- `functions/index.js:256-259` のコメントは本件を明記した上で exists ガードを**緩和として**置いている
- codex の推奨（`set(merge)` → `update()`）自体は正しい堅牢化 → **C の別 issue に吸収**

⚠️ **前セッションのメモリ記述の扱い**: 「ガードが実在する → よって作り直されない」という推論は
**結論は合っていたが理由が違った**。正しくは「**削除順序が**ガードの成立を保証している」。
メモリ `project-account-deletion-orphan-profiles.md` はこの理由に差し替えること。

### D2 — オフライン時にキャッシュの部分ページを「全件完了」と誤認 → **keep（major）** ★唯一の major
永続キャッシュは無効化されていない（`isPersistenceEnabled`/`cacheSettings` は grep 0 件＝既定で有効）。
成立する経路: ①step1 の delete がサーバ ack 済み → ②通信断 → ③step2 の `getDocuments()` がキャッシュへ
フォールバック（あるのは `fetchFollows(limit 30)` で過去に取った分だけ＝0 件 or 部分集合）→
④0 件なら `items.isEmpty` で即「完了」、k<50 件なら commit は再接続まで待ち成功後に `items.count < pageSize` で終了＝
**サーバ側の残りを再取得しない** → ⑤`deleteUserData` は成功扱い → `deleteAccount()` →
**Auth 消滅後は rules を満たせず、残った follows はクライアントから二度と消せない**。
general の反論は「開始時点でオフライン」にしか効かず、「step1 成功後に切れる」経路が残る。

### C — `users` 孤児の復活レース
step2 の N 件削除ごとに `onFollowDeleted` が非同期発火し各々 `userRef.get()`→`userRef.set(merge)`
（`index.js:288,293`）。step6 の delete が N 個の窓のいずれかに落ちる確率は **D1 と違い無視できない**
（本 PR が follows 削除を足したことで初めて生じる）。
ただし被害は「カウンタ 2 つだけの `users/{uid}`」で read は `isOwner` のみ（`rules:139`）＝
**誰にも見えず PII なし**。Admin SDK 掃除（既存孤児タスクと同じ回）で回収可能。
- **推奨**: Functions の `reconcileFollowCounters` を `set(merge:true)` → `update()` にする**別 issue**
  （D1 の残穴も同時に閉じる）。本 PR ではコメントを弱めるだけ
- ⚠️ **general 案「`users` 削除を step2 前へ繰り上げ」は非推奨**: 途中失敗 → プロフィール画面で
  `ProfileViewModel.swift:255-262` が users と **`publicProfiles` を自動再作成** → step1 で消した公開プロフィールが
  復活＝privacy-first と逆行。現順序なら users が残るため再作成は走らない
