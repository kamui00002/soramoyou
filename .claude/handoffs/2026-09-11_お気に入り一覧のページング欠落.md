## PR #102 の中身（設計の要点）

**真因は2層構造。**
- 下の層 = `fetchFavorites`（favorites 1ページ取得・アトミック。失敗すれば丸ごと throw）
- 上の層 = `fetchPost` で postId を1件ずつ解決（**部分的に失敗しうる**）

カーソルは下の層のものなのに `cursor = favorites.last?.createdAt` で**ページ末尾まで無条件に進めていた**。
そのため上の層でこぼれた投稿が「消費済み」になり、次ページはその先から始まる＝**二度と取りに行かれず静かに消える**。

→ ①**失敗地点でページを切り詰め**、カーソルは「解決を終えた最後の1件」まで（レジで30個スキャンして袋に25個なら、レシートは25個分で切る）
→ ②一覧0件だと末尾セルが無く `.onAppear` が発火しない → ViewModel 側で**最大5ページ繰る**。予算切れでも `hasMore` は倒さない（「全部消えました」＝嘘の断定になる）

⚠️ **「1件でも transient ならページ丸ごと捨てる」案は意図的に不採用**（1件の不調が29件を隠す＝症状が悪化する）。再提案しないこと。

#### simplifier の結果（未対応・すべて severity: low）

⭐️ **最重要の裏取り: `stalledWithMore` は派生状態ではない＝削ってはいけない。**
反例 = `pageSize=2` で1ページ目 `[p1, gone]` → `posts=[p1]`（非空・ループは止まる）・`hasMore=true`・`stalledWithMore=false`。
その後 `loadMore()` で続く5ページが全部 notFound → 予算切れ → `batch.posts` 空・`batch.hasMore=true` → `stalledWithMore=true`。
**このとき `posts=[p1]` は非空なので `hasMore && posts.isEmpty` は false になり取りこぼす。**
判別に使っているのは「今回のバッチが1件でも追加できたか」という**差分**で、View 側の `@Published` からは再構成できない。
`hasMore && posts.isEmpty` への置き換えは**ユーザーを詰みに置き去りにするリグレッション**。提案が再燃しても却下すること。

未対応の指摘（次セッションで judge にかけてから対応判断）:

1. **`stalledWithMore = batch.hasMore && batch.posts.isEmpty` が `load()` と `loadMore()` に一字一句重複**
   → `PageBatch` に `var stalled: Bool { hasMore && posts.isEmpty }` を生やして両方 `batch.stalled` に
2. **`PageResolution.consumed` の間接参照** — 呼び出し元で毎回 `favorites[consumed - 1].createdAt` に変換している
   → `PageResolution` に `cursor: Date?` を持たせ、打ち切り時 `index > 0 ? favorites[index-1].createdAt : nil` / 完走時 `favorites.last?.createdAt` を詰める
   ⚠️ **これはカーソル計算そのものを触るので、やるなら陽性対照を取り直すこと**（手順は下記）
3. **`resolvedPosts = []; unfavoritedIds = []; posts = []; hasMore = false` の4行が3箇所に重複**（未ログイン時 / 全滅時 / catch節）
   → `private func resetToEmpty()` に切り出す。`unavailableCount` / `lastError` / `loadMoreError` / `stalledWithMore` は箇所ごとに値が違うので呼び出し側に残す
   ⚠️ simplifier 自身が「3箇所のうち今回の PR で増えたのは1箇所だけかもしれず、Surgical Changes 的にこの PR でやるべきかは実装者判断」と留保している
4. （補足・対応不要と自認）View の「`loadMoreError != nil` なら再試行／そうでなければ続きを読み込む」の2択が3箇所に散っている

「無し」と判定された項目（再検討しないこと）: `PageResolution`/`PageBatch` の統合（レイヤーが違う・混ぜると累積 `+=` と単発 `=` が同居して事故る）／`fetchVisiblePages` と `resolvePosts` の分割（責務が明確に別）／`logTruncationIfNeeded`（`"(truncated)"` を1箇所に集約していて適切）／`emptyWithMoreDescription` とフッターの3分岐（画面状態が排他的）／テスト4本の重複（相補的）

⚠️ **4役を同時投入するとセッション制限を一気に食って全滅する**（前セッションで実際に4役とも 429 で落ちた）。**1役ずつ順に**投げること。

`reviewer-codex` には背景4点（目的・意図・制約・許容CC）を必ず渡す。制約は上記「意図的に不採用」の3点＋`fetchPost` の N+1 は承知の上（read rule が visibility 依存で `whereField(documentID, in:)` が使えない）。

simplifier に投げた重点（引き継ぎ候補）:

- `logTruncationIfNeeded` は関数にする価値があるか
