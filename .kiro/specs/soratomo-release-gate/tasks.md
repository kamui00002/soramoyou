# Implementation Plan

## 進め方の約束

- 作業はmainを取り込んだブランチで行い、コミットは日本語にする（mainへの直接コミット・pushはしない）。Functionsのデプロイは、mainを取り込んだブランチから行う（古いブランチから出すと既存の関数の設定が戻る）。
- 「（ユーザーのGOを取ってから実行）」と書いた操作は、利用者のGOを得るまで実行しない。AIが単独で実行しない。対象は次のとおり。ルールとFunctionsのデプロイ。secretの設定。本番のFirestore・Auth・Storageへのアクセス（読み取りだけの `find-orphans`、語のリストの投入、`delete-user`、`suspend` を含む）。TestFlightへの提出。App Store審査への提出。pushとPRの作成。
- firebase CLIには必ず `--project soramoyou-ios` を付ける（`.firebaserc` が空のため）。
- secretの値は、コマンドの引数・出力・ログ・チャットのどこにも出さない。設定は `firebase functions:secrets:set 名前` だけを実行し、値は対話の入力欄に入れる。
- 語のリストの中身（実在の語）は、リポジトリ・テスト・ログ・コミットメッセージ・チャットの記録に書かない。テストにはダミーの語（例「てすとごい」）を使う。
- 各テストは、先に「わざと壊した実装かルール」で期待外れになることを1回確かめてから、正しいもので通す（陽性対照）。陽性対照が取れなかったときは「検証済み」と書かず、取れなかった理由を記録する。
- design.mdの「要確認」9件は、確かめるまで「検証済み」と書かない。確かめる場所は次のとおり。1は3.2、2は1.2、3は3.4、4と7は14.5、5は16.2、6は4.5、8は16.4、9は14.1。
- Functionsのテストは、単体が `npm test`、エミュレーターが `npm run test:emulator`（firestoreとstorage）。7で登録するまでの間は、各タスクの中で `node --test` を直接使う。
- iOSのビルドとテストは、`uptime` で負荷を見てから、`nice -n 19` と少ない `-jobs` で1本ずつ行う（重ねて回すとMacごと落ちた先例がある）。テストのシミュレーターはC2E3F752を使う（共用の端末を壊さないため）。
- 新しいSwiftファイルは、プロジェクトの同期グループが自動で拾う。プロジェクトの設定ファイルは触らない。
- `(P)` を付けたタスクは、前提に書いたタスクが済んでいれば、ほかの `(P)` のタスクと同時に進めてよい（触るファイルと資源が重ならない）。付けていないタスクは、同じファイルを触るか、前のタスクの成果物に依存するか、エミュレーターやビルドを共有する。iOSのタスクは、ファイルが別でも、ビルド・DerivedData・シミュレーターが1つで1本ずつしか回せないので `(P)` を付けない。
- Functions側とiOS側は別の境界で、サーバーの契約はdesign.mdのAPI Contractで固定済みなので、別のセッションで並行して進めてよい。
- このtasks.mdに `textlint --fix` を掛けない（見出しの番号の後の空白が消える）。
