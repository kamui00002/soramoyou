# Requirements Document

## Project Description (Input)
そらとも 一般公開の切り替え（soratomo-public-launch）: 機能フラグ（カスタムクレーム soratomoBeta）の確認を、アプリ・Firestore/Storage ルール・Cloud Functions（Callable と通知の宛先の絞り込み）から外し、ログインした全員がそらともを使えるようにする。全員にクレームを配る案は採らない（公開する版で審査の人にもそらともが見える＝ガイドライン 2.3.1 の隠し機能扱いを避けるため）。切り替えの順番（サーバーを先に開けるか・版を先に配るか）、Android 版（別 worktree・同じ Firebase）への影響、App Check を強制していない点の扱い、公開前ゲートの残り（G3 What's New とオンボ＝PR #163・G4 計装の着弾・G5 プライバシーラベル等は利用者の手作業・release-gate tasks.md 19 の公開判断の記録）を含む。1.15.0 で「グループだけ抜ける」（別 spec soratomo-leave-group）と一緒に出す。

## Introduction
「そらとも」は、招待コードで参加する最大20人の非公開グループで、空の写真を見せ合う機能です（`.kiro/specs/soratomo/`、以下「soratomo spec」）。いまは機能フラグ（カスタムクレーム`soratomoBeta`）の内側にあり、クレームを付けた開発者とテスト用アカウントだけが使えます。公開前ゲートのG1（退会の削除）とG2（通報・ブロック・同意・NGワード）は、`.kiro/specs/soratomo-release-gate/`（以下「release-gate spec」）で完了し、1.14.0で公開済みです。

利用者が減っているので、そらともを1.15.0で、ログインした全員に公開します（2026-10-11の利用者の決定）。本書はその切り替えの要件を定めます。切り替えの方法は、アプリ・Firestore/Storageのルール・Cloud Functionsの3か所から、クレームの確認を外すことです。全員にクレームを配る案は採りません。公開する版で審査の人にもそらともが見えるようにし、App Store審査ガイドライン2.3.1の「隠し機能」の扱いを避けるためです。

同じ1.15.0に、「グループだけ抜ける」（`.kiro/specs/soratomo-leave-group/`、以下「leave-group spec」）が入ります。抜ける動きはleave-group specが定め、本書は1.15.0への同梱・切り替えの順序・新機能の案内（What's Newとオンボーディング）を持ちます。

早く出すために、範囲は小さく保ちます。公開に要らないものは「対象外」に送りました。本書は「何を満たすか」だけを定めます。関数名・判定の書き方・切り替えの細かい順序・テストの作り方は、設計で決めます。利用者の判断が要った事項は、末尾の「決定事項（2026-10-11）」にまとめました。要件の本文は、決定どおりに書いてあります。

## Requirements

### Requirement 1: そらともバックエンドのフラグの確認を外す
**Objective:** 開発者として、サーバーの判定からクレームの確認を外したい。これにより、全員にクレームを配らずに、ログインした全員へそらともを開ける。

#### Acceptance Criteria
1. **The** そらともバックエンド **shall** そらともの読み取りと書き込み（グループの作成・参加・招待コードの再発行・投稿・投稿の削除・通報・ガイドラインへの同意・画像の読み取りと保存と削除）を受け付けるかどうかを、要求した利用者のクレームの有無で決めない。
2. **The** そらともバックエンド **shall** 1の対象に、leave-group specで足す「グループを抜ける」の要求も含める。
3. **When** グループに新しい投稿が作成されたとき、**the** そらともバックエンド **shall** 新着通知の宛先を、受信者のクレームの有無で絞らない。
4. **The** そらともバックエンド **shall** 3の宛先を、soratomo specの要件9の規則（通知設定・ブロック・トークン・5分の間引き）で、これまでと同じく絞る。
5. **The** そらともバックエンド **shall** クレームの確認を外した後も、次の判定を外す前と同じ条件で行う: メンバー判定（soratomo specの要件11の1〜3）・投稿者本人の判定（同11の6・15）・ガイドラインへの同意（release-gate specの要件10）・NGワード（同11）・利用停止（同8）・人数と所属数の上限（soratomo specの要件11の10）。
6. **If** 未ログインの利用者からそらともの要求を受けた場合、**the** そらともバックエンド **shall** 外す前と同じく、その要求を拒否する。
7. **If** 匿名アカウントから、退会の削除を除くそらともの要求を受けた場合、**the** そらともバックエンド **shall** その要求を拒否する。
8. **The** そらともバックエンド **shall** 退会の削除（release-gate specの要件1〜3）を、外す前と同じく、クレームの有無と匿名かどうかに関わらず行う。
9. **The** そらともバックエンド **shall** 切り替えの途中と後も、1.14.xでクレームを持つ利用者の要求を、切り替えの前と同じく受け付ける。

補足: 7は、soratomo specの決定事項12（匿名アカウントでは使えない）を、サーバー側でも保つために設けました。いまはクレームが匿名アカウントを止めています。確認を外すと止めるものが無くなるため、同じ結果を別の判定で保ちます。iOS版とAndroid版には匿名で入る画面が無いので、利用者から見た変化はありません。判定の書き方は設計で決めます。

### Requirement 2: そらもようアプリのフラグの確認を外す
**Objective:** 利用者として、クレームが無くても、ログインしていればそらともを使いたい。これにより、招待された友達がすぐに参加できる。

#### Acceptance Criteria
1. **While** 登録済みの利用者がログインしている間、**the** そらもようアプリ **shall** ホームの「そらとも」の入口を、クレームの有無に関わらず表示する。
2. **While** 利用者が未ログイン（ゲスト中）または匿名アカウントである間、**the** そらもようアプリ **shall** そらともの入口・画面・通知の事前説明を表示しない（soratomo specの要件1の5のまま）。
3. **If** 起動したときに通信できない場合、**the** そらもようアプリ **shall** 登録済みの利用者には入口を表示する。通信が要る操作は、soratomo specの要件12のとおり扱う。
4. **While** 登録済みの利用者がログインしている間、**the** そらもようアプリ **shall** 通知設定の「そらとも通知」を、クレームの有無に関わらず表示する。
5. **While** 登録済みの利用者がログインしている間、**the** そらもようアプリ **shall** 退会の確認の文に、そらともの投稿とグループへの参加も削除されることを、クレームの有無に関わらず含める。
6. **When** 登録済みの利用者がそらともの新着通知をタップしたとき、**the** そらもようアプリ **shall** クレームの有無に関わらず、soratomo specの要件10の7〜9のとおりに処理する。

補足: 3は、いまの判定が起動ごとにIDトークンを取り直し、取れないと入口を隠すために設けました。公開後はクレームを読む理由が無いので、通信の状態で入口が消えないようにします。5は、release-gate specの要件3の7（対象はフラグONの利用者だけ）を上書きします。対象をフラグONの利用者に絞った理由（フラグOFFの利用者にそらともの名前を見せない）が、公開で無くなるためです。

### Requirement 3: 切り替えの順序と、各版の利用者の見え方
**Objective:** 利用者と審査の人として、切り替えのどの時点でも、壊れた画面（入口が出るのに、読み書きが拒否される画面）を見たくない。これにより、公開の作業中も安心して使える。

#### Acceptance Criteria
1. **While** 1.15.0が審査の人または利用者の手に渡っている間（審査への提出・TestFlightでのクレームの無いアカウントへの配布・App Storeでの公開）、**the** そらともバックエンド **shall** 要件1のすべての項目を満たした状態にある。
2. **While** Firestoreのルール・Storageのルール・Functionsのうち、一部だけが要件1の状態である間、**the** リリース手順 **shall** 1.15.0を審査に出さず、クレームの無いアカウントに配らない。
3. **When** そらともバックエンドを要件1の状態にしたとき、**the** リリース手順 **shall** 本番のルール2本とFunctionsが、mainに入れた変更と一致することを読み返して確かめてから、1.15.0を審査に出す。

### 1. 公開後の乱用への備えを、どこまで公開の前に入れるか

**決定: A. 既存の上限・匿名アカウントの拒否・公開後14日の見回りだけにする（推奨どおり・2026-10-11 利用者）**

確認を外すと、そらともバックエンドは「登録済みのアカウントでログインしていれば誰でも」受け付けます（前提と制約）。

| 選択肢 | 帰結 |
|---|---|
| A. 既存の上限・匿名アカウントの拒否・公開後14日の見回りだけにする | 公開を遅らせない。乱用は見回りで気づき、利用停止で止める。改造したアプリからの大量の投稿は、気づくまで通る |
| B. Aに加えて、1人1グループ1日20件の投稿の上限を、サーバー側でも判定する | 改造したアプリからの大量の投稿を止められる。Functionsの変更とテストが増え、公開が数日遅れる |
| C. Bに加えて、App Checkを強制し、要求の回数を制限する | 最も固い。iOS版とAndroid版の両方にApp Checkを組み込む作業が要り、公開が大きく遅れる。1.14.xはApp Checkのトークンを送らないので、強制すると先行公開の利用者の要求も拒否される |

- 推奨: A。早く出したいという動機に合います。既存の公開の機能（ルートの投稿・いいね・コメント）にもApp Checkは無く、そらともだけを厳しくする理由が弱いです。1人10グループ・1グループ20人の上限と招待コードがあるので、1人が他人へ届けられる範囲は小さいです。費用の膨らみは、見回りで気づけます。
- 反映先: 要件1の7・要件5・対象外。
